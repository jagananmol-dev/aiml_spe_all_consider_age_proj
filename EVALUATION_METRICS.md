# VEDA AI — Evaluation and Metrics

This document explains **how VEDA is evaluated**: which datasets are used, where the data came from, which questions are asked, how each metric is defined and computed, and the measured results for each dataset.

All numbers in this file were measured on **26 October 2026** with the scripts named next to them. They can be reproduced with the commands in [Section 7](#7-how-to-reproduce).

---

## 1. What is evaluated

VEDA is a retrieval-augmented generation (RAG) system. A user asks a question; the system searches the company's documents, picks passages, and a local LLM writes an answer that cites those passages. A knowledge graph built from the same documents boosts passages that mention entities connected to the question.

The evaluation tests the system in **two stages**, each with its own metrics:

| Stage | Question it answers | Script | Uses the LLM? |
|:--|:--|:--|:--:|
| **1. Retrieval** | Did the passage that contains the answer reach the LLM, and how high was it ranked? | `scripts/eval/retrieval_eval.py` | No |
| **2. End-to-end answer** | Is the final answer correct, and are its citations valid? | `scripts/demo/check_chat.py`, `scripts/enron/check_chat.py` | Yes |

Separating the two shows *where* a failure happens. If retrieval misses the evidence, the LLM cannot answer. If retrieval finds it but the answer is wrong, the generation step is at fault.

A third group of **system metrics** (latency, ingestion throughput, graph size) is reported next to them.

## 2. The two datasets

VEDA is evaluated on two companies (tenants) that are deliberately opposite:

| | **Nephrova Renal Care** | **Enron Corp.** |
|:--|:--|:--|
| Type of data | **Synthetic**, generated by us | **Real**, public records |
| Industry | Healthcare (outpatient dialysis) | Energy trading and corporate finance |
| Documents | 72 | 3,123 |
| Formats | 8 (PDF, Word, PowerPoint, Excel, CSV, JSON, Markdown, text) | Plain text (email bundles, SEC filings, policies) |
| Text size | ≈ 1 MB | ≈ 318 MB |
| Ground truth | **Complete**: every fact comes from one generator file | **Partial**: every expected answer checked by hand in the source |
| Noise | None by design | Duplicates, forwarded threads, signatures, bad encodings, wrong dates |
| Tests mainly | Correctness, policy reasoning, cross-document links | Scale, robustness, real-world retrieval |
| Workspace slug | `nephrova` | `enron` |

Synthetic data gives exact ground truth but is cleaner than any real company. Real data is messy and large, but its ground truth must be checked by hand. Using both covers the weaknesses of each.

### 2.1 Nephrova: how the synthetic data was made

**The company.** Nephrova Renal Care Pvt. Ltd. is a **fictional** company that runs outpatient haemodialysis for people with chronic kidney disease. It has three centres in Pune (Kothrud, Hadapsar, Pimpri), 30 dialysis machines, 238 active patients and 74 staff. All people are fictional. Patients appear only as de-identified IDs, so the dataset contains no personal data.

**One source of truth.** Every name, date and number lives in a single Python file, `scripts/demo/company.py`. It holds:

- the company profile, the 13 named staff and the three centres with their machines;
- monthly session counts, the payer mix (PM-JAY 45%, self-pay 35%, insurance 20%) and the rates. Revenue and EBITDA are **computed** from these, not typed by hand;
- water-quality limits (endotoxin max 0.25 EU/mL, action level 0.125);
- the HR and finance rules (notice periods, shift allowances, approval limits, increments, travel rates);
- the facts of each storyline (alarm dates, lab results, infection cases, accreditation findings).

**The generator.** `scripts/demo/generate_dataset.py` (≈ 1,600 lines) reads `company.py` and writes the documents. It is **deterministic**: it uses no random numbers, so every run produces the same files and the same ground truth.

- Each document is registered with a date, a format and a builder function. Real format libraries write the files: PyMuPDF for PDF, python-docx for Word, openpyxl for Excel, python-pptx for PowerPoint, plus CSV, JSON/JSONL, Markdown and text writers.
- There is **one or more documents per day from 30 July to 9 October 2026**. `demo-data/nephrova-manifest.json` records each file's date, and uploads are backdated to that date, so the tenant looks like a company that uploaded its paperwork day by day.
- There are no images, so OCR quality does not affect the results.

**What the 72 documents contain.**

| Group | Examples |
|:--|:--|
| Policies | 6 HR policies (conduct, recruitment, compensation, appraisal, POSH, leave), 5 finance policies (delegation of authority, billing, refunds, procurement, travel), clinical SOPs (infection control, hand hygiene, water treatment, waste, catheter care) |
| Daily operations | Shift logs, machine alarm logs, biomedical job reports, water lab results, disinfection records, rosters, census and stock sheets |
| Management reporting | Monthly operations reviews, finance MIS for August and September, Q3 quality report, board note, Q3 board pack |
| Long connected documents | Operations manual, risk and asset register, Q3 board pack |

By format: 12 PDF, 12 Word, 11 Markdown, 10 text, 9 Excel, 6 CSV, 6 JSON, 6 PowerPoint = **72**.

**Planted storylines.** To test reasoning across documents, four stories run through many files, each told from different angles in different formats:

1. **Machine HD-K04**: repeated conductivity alarms, then the service request, the job report and the repair (conductivity cell replaced).
2. **Water plant RO-H1 at Hadapsar**: an endotoxin result of 0.31 EU/mL (limit 0.25), the incident report, 64 sessions moved to Kothrud, the root-cause analysis (missed disinfection) and the passing resample.
3. **Catheter infections at Pimpri**: infection reports, the vancomycin treatment, an audit, an action plan, staff training, and hand-hygiene compliance rising from 78% to 94%.
4. **NABH accreditation**: the readiness checklist, briefing, surveillance assessment (3 minor findings) and corrective-action tracker.

`scripts/demo/validate_graph.py` checks that every file names the company and that the expected links between documents exist.

### 2.2 Enron: where the real data came from

**Why Enron.** It is the only large public collection of a real company's **internal** documents. The US Federal Energy Regulatory Commission (FERC) released the email during its investigation, and Carnegie Mellon University (CMU) cleaned and published it. Enron's SEC filings from the same years are public records. Together they show the company from inside (email) and from outside (official filings) over the same period, 1999 to 2002, including its collapse.

**Sources.**

| # | Source | Where from | What we took | Script |
|:--|:--|:--|:--|:--|
| 1 | **CMU Enron Email Dataset**, May 2015 release | `https://www.cs.cmu.edu/~enron/` (443 MB tar.gz) | 517,401 message files from 150 employees' mailboxes | `scripts/enron/build_emails.py` |
| 2 | **SEC EDGAR filings**, Enron CIK 1024401 | `https://www.sec.gov/cgi-bin/browse-edgar?action=getcompany&CIK=1024401` | 20 filings: two 10-K, six 10-Q, two DEF 14A, ten 8-K, including the Nov 2001 restatement and the Feb 2002 Powers Report | `scripts/enron/fetch_sec.py` |
| 3 | **Enron company policies** | The July 2000 Code of Ethics booklet (Wayback Machine copy of the public scan), a US DOJ trial exhibit, and policy announcements found in the email corpus | 39 policy documents | `scripts/enron/build_policies.py` |

**How it was prepared.**

*SEC filings (`fetch_sec.py`).* The script downloads each filing's full submission from EDGAR with an identifying User-Agent, as SEC requires. It keeps the main document and its press-release exhibits (`EX-99*`), drops financial data schedules and graphics, reduces HTML/SGML to plain text, and writes the form, filing date and source URL at the top of each file.

*Emails (`build_emails.py`).*

1. **Read** all 517,401 files. The corpus names files `1.`, `2.` … with a trailing dot, which Windows silently strips, so files are opened through `\\?\` long paths.
2. **Filter by date** to January 1999 – June 2002. The corpus has stray dates such as 1979 and 2044.
3. **Deduplicate.** The same email appears in several folders and mailboxes. Two messages are duplicates when sender, timestamp, subject and the start of the body match. Sent folders are read first and catch-all folders (`all_documents`, `deleted_items`, …) last, so each email is kept from its proper folder.
4. **Clean** bodies: remove `>` quoted lines, fix encoding errors, and cap each body at 3,000 characters.
5. **Name the owner** of each mailbox from the `X-Folder` header, not the sender, because assistants wrote most of the executives' sent mail.
6. **Bundle** emails into **one document per mailbox per month**, split above 250,000 characters. Each email starts with a `=== Email` header line, and the chunker splits on it, so passages and citations still point to single emails.

Result: **254,402 unique emails in 3,064 documents** (314 MB).

*Policies (`build_policies.py`).* The 65-page Code of Ethics is a scanned PDF with no usable text, so it was OCR'd page by page with VEDA's own OCR. The 37 policies announced by email (risk management and VaR limits, email and document retention, passwords, HR, conflict of interest…) are each saved at full length from their longest copy in the raw corpus.

**Totals:** 3,064 email documents + 20 filings + 39 policies = **3,123 documents**.

**Domain vocabulary as data.** `scripts/enron/graph_schema_enron.json` adds Enron's special-purpose entities (LJM, Chewco, JEDI, Raptor…), business units, finance issues and regulators to the knowledge graph. It is stored in the tenant's settings. No code was changed, which tests VEDA's claim that a new industry needs only configuration.

**Licence and privacy.** EDGAR filings are public records. CMU publishes the email corpus for research and asks users to respect the people involved. The raw data is therefore **not committed** to the repository: it is downloaded into `.data/` (gitignored) by the scripts and used only for a local demo.

## 4. Metric definitions

Notation: Q is the question set, |Q| its size. For question q, A_q is the set of acceptable answer alternatives, each a set of key strings. R_k(q) is the top k passages returned by retrieval, and ŷ_q is the generated answer.

### 4.1 Retrieval metrics (stage 1)

A passage is **relevant** to q when it contains **every** key string of at least one answer alternative (case-insensitive). This is a strict test: the passage must hold the full evidence, not just mention the topic.

**Hit@k** (also called Recall@k for a single gold item): the share of questions with a relevant passage in the top k.

```
Hit@k = (1/|Q|) · Σ_q 1[ some passage in R_k(q) is relevant ]
```

It is reported for k = 1, 3, 5 and 8. **k = 8 matters most**, because the chatbot sends the top 8 passages to the LLM (`final_top_k = 8`). Hit@8 is therefore the **context recall**: the share of questions where the LLM received the evidence.

**MRR (Mean Reciprocal Rank)**: how high the first relevant passage is ranked, on average.

```
MRR = (1/|Q|) · Σ_q 1 / rank_q          (a question with no relevant passage adds 0)
```

MRR = 1.0 means the evidence was always ranked first, and 0.5 means second on average. Rank matters because small local LLMs use the top passages more reliably than the rest.

**Graph-boost ablation.** Every retrieval metric is measured twice: with the knowledge-graph boost on (δ = 0.05, the default) and off (δ = 0). The difference shows what the knowledge graph adds to retrieval.

### 4.2 Answer metrics (stage 2)

**Answer accuracy**: the share of answers that contain every key string of at least one alternative.

```
Accuracy = (1/|Q|) · Σ_q 1[ ∃ a ∈ A_q : every string s ∈ a appears in lower(ŷ_q) ]
```

**Citation validity**: the share of answers whose citations `[n]` all point to a passage that was actually sent (1 ≤ n ≤ number of passages). An invalid citation would send the user to a source that does not exist.

```
CitationValidity = (1/|Q|) · Σ_q 1[ cites(ŷ_q) ⊆ {1, …, n_q} ]
```

### 4.3 System metrics

| Metric | Definition |
|:--|:--|
| Retrieval latency p50 / p95 | Median and 95th-percentile time of the full retrieval step (`RAGPipeline.prepare`), one call per question, after a warm-up query |
| End-to-end time | Time from sending a question to the last token of the answer |
| Graph size | Nodes and edges in the tenant's knowledge graph |
| Ingestion throughput | Passages indexed per second |

### 4.4 Why these metrics and not others

- **Key-string match instead of an LLM judge.** It is exact, free and repeatable, and needs no second model. Its weakness: an answer that contains the right number with wrong reasoning still passes. Faithfulness scoring (for example RAGAS) is listed as future work.
- **Hit@k and MRR instead of nDCG.** Each question has one decisive piece of evidence, not a graded list, so binary relevance fits. nDCG adds nothing with binary single-gold relevance.
- **No precision@k.** Many passages can be partly relevant, and labelling them all by hand is costly. Hit@k is the standard measure for "did the evidence arrive".

## 5. Results

**Setup:** laptop with an Intel i5-13450HX, 16 GB RAM, RTX 3050 6 GB. Embeddings: `all-MiniLM-L6-v2` (384 dimensions, on CPU). LLM: `llama3` 8B via Ollama (`num_ctx` 6144). Local mode with the in-memory vector index. Retrieval settings: `vector_top_k` 15, `final_top_k` 8, `min_similarity` 0.25, graph boost δ = 0.05.

### 5.1 Retrieval (stage 1)

| Dataset | Variant | Hit@1 | Hit@3 | Hit@5 | **Hit@8** | **MRR** | p50 ms | p95 ms |
|:--|:--|--:|--:|--:|--:|--:|--:|--:|
| **Nephrova** (22 q) | graph boost on | 0.64 (14/22) | 0.77 (17/22) | 0.95 (21/22) | **1.00 (22/22)** | **0.748** | 31 | 66 |
| | graph boost off | 0.64 (14/22) | 0.77 (17/22) | 1.00 (22/22) | 1.00 (22/22) | 0.749 | 15 | 51 |
| **Enron** (14 q) | graph boost on | 0.21 (3/14) | 0.71 (10/14) | 0.79 (11/14) | **0.79 (11/14)** | **0.467** | 24,381* | 93,112* |
| | graph boost off | 0.14 (2/14) | 0.57 (8/14) | 0.64 (9/14) | 0.71 (10/14) | 0.371 | 23,939* | 82,899* |

\* Measured while ingestion was writing new passages. See 5.3.

**Rank of the first relevant passage, per question** (graph boost on; `–` = not in the top 8):

- Nephrova: 1, 1, 2, 1, 1, 1, 3, 6, 4, 2, 5, 1, 1, 1, 1, 1, 1, 1, 4, 1, 1, 4
- Enron: –, –, 2, 2, 2, 1, 2, 2, 1, –, 1, 3, 5, 2

**What the results show:**

- **Nephrova: the evidence always reaches the LLM.** Hit@8 = 1.00. It is ranked first for 14 of 22 questions, never lower than 6th, and its mean rank is 2.0 (MRR 0.75).
- **Enron is much harder.** MRR drops from 0.75 to 0.47, and 3 of 14 questions miss the evidence:
  1. *Enron's total revenues in 2000* and 2. *net income as reported vs restated*: the figures sit inside wide financial tables in the 10-K and 8-K. Number-heavy table rows embed poorly, so they don't match the question's wording.
  3. *What the anonymous August 2001 letter warned about*: the relevant email bundle is not fully indexed yet.
- **The knowledge graph helps on real data.** On Enron the graph boost raises MRR by **+0.096 (0.371 → 0.467, +26%)**, Hit@3 from 0.57 to 0.71, and Hit@8 from 0.71 to 0.79. It moved the restatement-partnerships evidence from rank 5 to rank 2, and found Skilling's resignation reason (rank 1) that plain dense search missed. Enron's entities (LJM, Chewco, Skilling, Dynegy) are exactly what the graph links.
- **On Nephrova the graph is neutral.** The small synthetic corpus is already easy for dense search (MRR 0.748 vs 0.749). One question moved from rank 5 to 6, which costs Hit@5 but not Hit@8.

### 5.2 End-to-end answers (stage 2)

| Dataset | Questions | **Answer accuracy** | **Citation validity** | End-to-end time per question |
|:--|--:|--:|--:|--:|
| **Nephrova** | 22 | **1.00 (22/22)** | **0.95 (21/22)** | a few seconds (first token ≈ 1.7 s) |
| **Enron** | 14 | **0.71 (10/14)** | **1.00 (14/14)** | 27–59 s* (search 23–54 s of that) |

\* Dominated by the index rebuilds during ingestion (5.3), not by the LLM.

**Nephrova by category:** single-fact 12/12, policy application 6/6, cross-document 4/4. The one invalid citation was in the board-pack answer, which cited `[7]` when fewer passages were sent. The chat page drops such numbers, so the user never sees a broken link, but it is still counted here.

**Enron by source:** SEC filings 4/6, emails 3/5, policies 3/3.

**Every Enron failure, and its cause:**

| Question | Retrieval (5.1) | Answer given | Cause |
|:--|:--|:--|:--|
| Total revenues in 2000 | Not in top 8 | Not found | Figure is inside a 10-K financial table; **retrieval failure** |
| 2000 net income, reported vs restated | Not in top 8 | Incomplete | Same: figures in a table in the restatement 8-K; **retrieval failure** |
| What the anonymous Aug 2001 letter warned about | Not in top 8 | "I couldn't find any information…" | Evidence not yet indexed. The model **correctly abstained** instead of guessing. |
| Skilling's public reason for resigning | Counted as a hit at rank 1 | Quoted a **December 2000** email ("ready for a somewhat different role") | The rank-1 passage contains the word "personal" but in an unrelated email, so the substring metric gave a **false-positive retrieval hit**. The model then used a passage from the wrong date: a **temporal-grounding error**. |

So 3 of the 4 Enron failures trace back to retrieval, and 1 to generation (wrong time period). No answer invented a fact that was absent from the passages.

**Combining the two stages** (questions where the evidence was in the top 8 *and* the answer passed):

| Dataset | Evidence retrieved | …and answered correctly | Evidence missing | …but answered correctly anyway |
|:--|--:|--:|--:|--:|
| Nephrova | 22 | 22 | 0 | 0 |
| Enron | 11 | 10 | 3 | 0 |

When the evidence reaches the LLM, it answers correctly in **32 of 33 cases (97%)** across both datasets. When it doesn't, it never gets the answer right by luck. **Retrieval is the main factor in end-to-end accuracy.**

### 5.3 System metrics

| Metric | Nephrova | Enron |
|:--|--:|--:|
| Retrieval latency p50 / p95 (this run) | 31 / 66 ms | 24.4 / 93.1 s* |
| Dense search alone (in-memory index, cached) | 6–26 ms | not yet measured at full size |
| Graph size | 166 nodes, 378 edges | 11,981 nodes, 43,403 edges |
| Graph extraction time | ≈ 12 ms per document | 0.9 s for the 2000 10-K (was 27 s before the fix) |
| Ingestion throughput (CPU) | — (72 documents in minutes) | ≈ 12–15 passages/s |
| Median time to first token | 1.7 s | — |
| Generation speed | ≈ 23 tokens/s (llama3 on RTX 3050) | same |

\* **Why Enron retrieval is slow right now:** the in-memory index for a tenant is rebuilt whenever that tenant's passages change. During this run the ingestion worker added passages between almost every question, so most queries rebuilt an index of about 90,000 passages. Once ingestion finishes, the index is built once and cached, and search should drop to milliseconds as it does on Nephrova. This must be re-measured after ingestion.

## 6. Summary for the report

| Metric | Nephrova (synthetic) | Enron (real) |
|:--|:--:|:--:|
| Questions | 22 | 14 |
| **Context recall (Hit@8)** | **1.00** | **0.79** |
| **MRR** | **0.748** | **0.467** |
| Hit@1 | 0.64 | 0.21 |
| Graph boost effect on MRR | ±0.00 | **+0.096** |
| **Answer accuracy** | **1.00 (22/22)** | **0.71 (10/14)** |
| Citation validity | 0.95 | 1.00 |
| Answer accuracy when evidence was retrieved | 22/22 | 10/11 |
| Retrieval latency p50 | 31 ms | 24 s (during ingestion) |

**Main findings.**

1. On clean, structured company documents, VEDA always retrieves the evidence and answers almost all known-answer questions correctly with a small local LLM.
2. On real, noisy data at about 100× the size, retrieval is the bottleneck, above all for **numbers inside financial tables**.
3. The knowledge graph adds little on a small clean corpus but **clearly improves ranking on real data**, where entity names connect evidence across thousands of emails.

**Threats to validity.**

- The question sets are small (22 and 14) and were written by the team that built the system.
- Key-string matching cannot detect correct numbers with wrong reasoning. It can also count a passage as relevant when the key word appears in an unrelated context (the Skilling question in 5.2).
- Enron was measured during partial ingestion. Its email-based questions and its latency must be re-measured when ingestion completes.
- Retrieval thresholds (min similarity 0.25, boost 0.05) were tuned on Nephrova.

**Next evaluation steps:** re-run everything after Enron ingestion finishes, add a faithfulness metric (LLM judge or human labels), hand-label entities to report extraction precision/recall/F1, and test table-aware chunking or BM25 hybrid search for financial tables.

## 7. How to reproduce

Start the stack (`pnpm dev`) so that PostgreSQL, the services and Ollama are running. Then:

```bash
# 1. Build the datasets (ingestion venv)
services/ingestion/.venv/Scripts/python.exe scripts/demo/generate_dataset.py     # Nephrova: 72 files
services/ingestion/.venv/Scripts/python.exe scripts/demo/seed_tenant.py
services/ingestion/.venv/Scripts/python.exe scripts/enron/fetch_sec.py           # Enron: SEC filings
services/ingestion/.venv/Scripts/python.exe scripts/enron/build_emails.py        # needs the CMU tarball in .data/enron-raw
services/ingestion/.venv/Scripts/python.exe scripts/enron/build_policies.py
services/ingestion/.venv/Scripts/python.exe scripts/enron/seed_tenant.py

# 2. Retrieval metrics: Hit@k, MRR, latency, graph ablation (intelligence venv, no LLM)
services/intelligence/.venv/Scripts/python.exe scripts/eval/retrieval_eval.py --json eval.json
services/intelligence/.venv/Scripts/python.exe scripts/eval/retrieval_eval.py --tenant nephrova

# 3. End-to-end answer accuracy and citation validity (needs the web app and Ollama)
services/ingestion/.venv/Scripts/python.exe scripts/demo/check_chat.py
services/ingestion/.venv/Scripts/python.exe scripts/enron/check_chat.py
```

| File | Role |
|:--|:--|
| `scripts/demo/company.py` | Ground truth for Nephrova (all facts) |
| `scripts/demo/generate_dataset.py` | Writes the 72 synthetic documents |
| `demo-data/nephrova-manifest.json` | Upload date of each document |
| `scripts/enron/fetch_sec.py`, `build_emails.py`, `build_policies.py` | Build the Enron documents from public sources |
| `scripts/enron/graph_schema_enron.json` | Enron's graph vocabulary (configuration, not code) |
| `scripts/demo/check_chat.py`, `scripts/enron/check_chat.py` | Question sets and answer checks |
| `scripts/eval/retrieval_eval.py` | Retrieval metrics and graph ablation |
